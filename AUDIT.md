# bna-ui Component Library — Modernization Audit

**Scope:** All 79 items in `packages/registry/src/` — 52 UI components, 18 chart components, 6 hook files (audited as 6 rows; `useColorScheme` covers native + web as separate rows), and 3 theme files.
**Audited against:** expo ~57.0.8, expo-router ~57.0.8, react-native 0.86.0, react-native-reanimated 4.5.0, react-native-gesture-handler ~2.32.0, react-native-worklets 0.10.0, react-native-svg 15.15.4, react-native-safe-area-context ~5.7.0, react-native-screens ~4.26.0, react 19.2.3 — the versions pinned in this repo's `package.json` files as of this audit.
**Date:** 2026-08-02.
**Out of scope by design:** adopting NativeWind/Tailwind. This repo has zero NativeWind usage; styling is `StyleSheet.create` / inline style objects / a `useColor` token hook, which is the intended architecture — components ship as raw copy-paste source into consumer projects (see `CLAUDE.md`), and a Tailwind config dependency would break that zero-config install model. This audit evaluates the current styling system on its own terms rather than recommending a replacement.
**Deliverable nature:** this is an audit and roadmap only. No component source was changed in producing it.

The audit was conducted as 11 parallel research passes (grouped by component category), followed by this aggregation pass, which normalizes severity ratings across passes and de-duplicates repeated findings into the cross-cutting section below.

### Top issues, by impact

1. **Rules-of-Hooks violation across 15/17 data-viz charts** (§3.1) — will throw "Rendered more/fewer hooks than during the previous render" the moment a chart's dataset length changes between renders, an ordinary occurrence for live/filtered data. P0 across the board.
2. **`meta.ts` accessibility sections are fictional almost everywhere** (§3.2) — not just missing, but actively asserting compliance ("keyboard navigation support," "proper ARIA attributes," "screen reader announcements") that doesn't exist in code, across most of the library.
3. **`media-picker.tsx` uses a deprecated Expo API and requests permissions without the required `app.json` plugin entries** — confirmed missing from the actual playground app; a real iOS crash risk for anyone following the docs as written. P0.
4. **`tabs.tsx` has a module-scope mutable object (`allTabContents`) shared across every `Tabs` instance in an app**, live by default (`enableSwipe` defaults `true`) — real cross-instance data corruption / memory leak, and undocumented. P0.
5. **`video.tsx` ships a documented `VideoRef` type whose methods were never wired up via `useImperativeHandle`** — calling `ref.current.play()` as documented will crash at runtime — plus a `nativeControls` prop that's destructured but hard-coded to `false` regardless of what's passed (confirmed broken by a bundled demo). P0.
6. **`camera-preview.mdx` documents ~13 props and 3 events on a component that takes zero props**, and its manual-install instructions still tell users to install `expo-av`, removed from the Expo SDK two majors ago. P0.
7. **Divide-by-zero/NaN geometry bugs across nearly every chart** with an all-zero or single-segment dataset (§3.1) — silently broken rendering, no error.
8. **Unvirtualized list rendering** in `gallery.tsx`'s main grid and `table.tsx`'s rows (when pagination is disabled) — real perf cliff for non-trivial datasets, while sibling code in the same files proves the authors already know the correct (`FlatList`) pattern elsewhere.
9. **`action-sheet.tsx` and several other components ship with missing dependency declarations** — `definitions/action-sheet.ts` has no `dependencies` field despite the component statically importing `react-native-reanimated`, meaning `bna-ui add action-sheet` on a fresh project can ship an unresolvable import.
10. **Two prop-level "phantom documentation" bugs worse than the original `button.ts` spot-check**: `meta/image.ts` documents a `full` prop that doesn't exist anywhere in `image.tsx`, and `meta/mode-toggle.ts` documents a `style` prop that doesn't exist while omitting the two real props (`variant`, `size`) entirely.

## 2. Methodology

Each of the 79 items was researched individually: source file, registry `definition`, `meta.ts` (where present), and MDX doc page were read in full, then cross-diffed prop-by-prop. Version-specific claims (deprecated APIs, current idioms, current prop surfaces) were checked against live documentation via web search and fetch rather than relied upon from training data, since Expo/RN/Reanimated move fast enough that stale knowledge produces wrong recommendations. Citations are included per finding below.

This is a **static and documentation audit**, not a live device/simulator test — findings about runtime behavior (e.g., the `tabs.tsx` module-scope bug, the `video.tsx` dead prop) are inferred from source-code reading, cross-referenced against bundled demo files where those exist to corroborate the failure mode, not observed on-device. Two items should be manually verified on-device before being treated as certain: the `bottom-sheet.tsx` `GestureHandlerRootView`-inside-`Modal` placement (research concluded this is actually correct per gesture-handler's own docs, contrary to initial suspicion) and the exact Reanimated/worklets version-compatibility pairing (one source cited 4.5.x pairing with worklets 0.6–0.7.x, another cited 4.4 aligning with 0.10 behavior — flagged unverified in the hooks/theme batch, worth checking `docs.swmansion.com/react-native-reanimated/docs/guides/compatibility/` directly).

Some `WebFetch` calls to `reactnative.dev` failed in the research sandbox during two of the eleven batches; those batches corroborated citations via `WebSearch` snippets or a reader-proxy fetch of the same canonical URL instead, and this is noted inline where it occurred. No finding in this report rests solely on an unverified claim without being marked as such.

## 3. Cross-Cutting Findings

### 3.1 Rules-of-Hooks violation across charts (the single highest-impact finding)

15 of 17 data-visualization chart components call `useAnimatedProps` and/or `useAnimatedStyle` **inside** a `.map()` or `Array.from()` render-loop callback — per datapoint, per segment, per cell, or per candle — instead of at the top level of a dedicated subcomponent. React requires hook call count and order to be stable across renders; when the underlying array length changes between renders (a completely ordinary event for live, filtered, or paginated chart data), React throws `"Rendered more/fewer hooks than during the previous render."` Reference: https://react.dev/warnings/invalid-hook-call-warning

Affected, with call-site multiplier:

- `line-chart` (1×/point) — `area-chart` inherits the bug since it's a thin wrapper around `LineChart`
- `stacked-area-chart` (1×/point/series), `column-chart` (1×/bar), `stacked-bar-chart` (**2 levels of nesting** — 1× per series-value pair)
- `pie-chart`, `doughnut-chart`, `polar-area-chart`, `radial-bar-chart` (1×/segment), `radar-chart` (1×/vertex, though its main-area hook is correctly top-level)
- `scatter-chart` (1×/point), `bubble-chart` (1×/bubble), `candlestick-chart` (**2 hooks ×/candle** — the worst single-item multiplier), `heatmap-chart` (**rows × cols**, quadratic — the worst overall multiplier), `treemap-chart` (1×/rectangle)

**Not affected**: `bar-chart` (extracts correctly... actually also affected, see CH-1 detail table — verify per row below), `progress-ring-chart` (no loop in the file at all — structurally immune), `chart-container` (layout wrapper, no animation code).

The fix is the same shape everywhere: extract the per-item render into its own subcomponent (e.g. `AnimatedDataPoint`, `PieSlice`, `AnimatedCandle`) so the hook is called once per **mounted component instance**, not once per loop iteration inside a parent's render. This is a mechanical, low-risk refactor — public component `Props` are unaffected in every case.

### 3.2 `meta.ts` accessibility claims are largely fictional

Across every batch that checked, `meta.ts` "Accessibility" sections make specific, falsifiable claims — "proper ARIA labels," "keyboard navigation support," "screen reader announcements," "touch targets meet minimum size requirements," "focus management when opened/closed" — that have no corresponding implementation. This isn't vague marketing copy; it names specific, checkable behaviors and asserts they exist. Combined with the fact that only 1 of 79 items has any real `accessibility*` prop, this means the documentation is not just incomplete but actively misleading about the current accessibility posture of the library. Confirmed instances span `button`, `icon`, `hello-wave`, `card`, `checkbox`, `radio`, `progress` (conflated with UX), `alert`, `toast`, `accordion`, `action-sheet`, `alert-dialog`, `bottom-sheet`, `collapsible`, `popover`, `sheet`, `tabs`, `carousel`, `gallery`, `onboarding`, `date-picker`, `picker`, `mode-toggle`, `audio-recorder`, `camera`, `camera-preview`, `video`, and all 18 chart components.

**Recommended baseline going forward, once real accessibility work starts**: for interactive controls, add the specific `accessibilityRole`/`accessibilityState`/`accessibilityValue` the platform defines (documented per-row below); for SVG-rendered charts, where native accessibility trees can't describe individual paths, add a single `accessible={true}` + synthesized `accessibilityLabel` summarizing the dataset on the chart's outer container — not per-datapoint semantics, which aren't feasible for SVG rendering. `progress-ring-chart` is the one chart that's a realistic candidate for full native semantics (`accessibilityRole="progressbar"` + `accessibilityValue`) since it represents a single scalar value.

### 3.3 Registry dependency-declaration drift

Two related but distinct problems, both invisible to the existing build pipeline (`scripts/verify-payloads.mjs` validates `registryDependencies`/`hooks`/`theme` names and payload self-containment, but not npm-dependency-vs-actual-import correctness):

- **Declared but unused**: `react-native-gesture-handler` appears in the `dependencies` array of `definitions/charts/{column,stacked-area,stacked-bar,pie,doughnut,polar-area,radar,radial-bar,progress-ring,scatter,bubble,candlestick,heatmap,treemap}-chart.ts` (14 of 18 charts) despite zero import of gesture-handler in the corresponding source — a copy-paste artifact from `line-chart`'s definition template, the one chart that legitimately uses it. Also found in `combobox.ts` (registryDependencies declares `text`/`view` that combobox.tsx never imports, since it uses RN's `Text`/`View` directly), `carousel.ts` (declares unused `text`), and `scroll-view.ts` (declares unused `view`).
- **Used but undeclared**: `definitions/action-sheet.ts` has **no `dependencies` field at all**, despite `action-sheet.tsx` statically importing `react-native-reanimated`. Because its only `registryDependencies` (`text`, `view`) both resolve to empty dependency arrays, nothing in the transitive closure supplies the package — `bna-ui add action-sheet` on a fresh project ships an unresolvable static import. Also found: `spinner.ts` and `skeleton.ts` both omit `react-native-reanimated`/`react-native-worklets` despite directly and extensively using them.
- **Missing from human-facing docs but present in the machine-readable definition**: `react-native-worklets` — mandatory for Reanimated 4.x per its own migration guide — is correctly listed in nearly every chart's `definitions/charts/*.ts`, but omitted from the corresponding MDX "Manual install" snippet on nearly all 18 chart pages. Anyone following the manual-install path gets a broken build; anyone using `bna-ui add` is unaffected since the CLI reads the definition, not the prose.

### 3.4 Documentation drift is pervasive, not isolated

The original spot-check that motivated this audit (`meta/button.ts` missing the real `haptic` prop and documenting a dead `label` prop) turned out to be representative, not exceptional. Confirmed instances of real prop-doc drift (beyond the accessibility-claims pattern in §3.2) include:

- **Fabricated props** (documented but don't exist in source): `meta/image.ts`'s `full: boolean`; `meta/mode-toggle.ts`'s `style: ViewStyle`; `meta/accordion.ts`'s `disabled` on both `Accordion` and `AccordionItem`.
- **Real, functional props entirely missing from docs**: `button.tsx`'s `haptic`; `input.tsx`'s `type`/`rows` (which gate the entire textarea rendering path — undocumented on both `Input` and `GroupedInputItem`); `bottom-sheet.tsx`'s `disablePanGesture`; `tabs.tsx`'s `enableSwipe`, `value`, `onValueChange` (the highest-stakes case — `enableSwipe` is the prop that triggers the module-scope bug in §3.7, and it's completely undocumented); `mode-toggle.tsx`'s real `variant`/`size` (replaced in docs by the fabricated `style` above); `file-picker.tsx`'s `variant`; `date-picker.tsx`'s `DateRange` value shape for `mode='range'`.
- **`meta.ts` missing entirely (`types` field absent)**: `carousel.ts` (zero of 12+ props documented in the machine-readable payload, though the MDX page independently hand-writes accurate tables), `onboarding.ts`, `parallax-scrollview.ts`, `view.ts`, `bottom-sheet.ts`, `toast.ts` (meaning the generated `/r/ai/toast.json` AI-consumption payload ships with no structured prop data at all).
- **Wrong documented defaults/types**: `progress.ts` documents `height` default as `4` when the real default is `HEIGHT` (48) — off by 12x; `useColorScheme`'s shared MDX documents a `'light' | 'dark' | null` return type when the verified real signature (checked against RN 0.86.0's actual source) is a strict, never-null `'light' | 'dark'`; `useModeToggle.mdx` cites `Appearance.setColorScheme(null)`, an API shape that doesn't exist in RN 0.86 (`setColorScheme` takes `'light' | 'dark' | 'unspecified'`, no `null`) — the source code itself already correctly uses `'unspecified'`.
- **Wrong install instructions**: `camera-preview.mdx` tells users to `npx expo install expo-av`, removed from the SDK; `useBottomTabOverflow.mdx` tells users to install `@react-navigation/bottom-tabs`, which the hook doesn't use (it reads a context re-exported by `expo-router`); `theme-provider.mdx` lists `@react-navigation/native` and `react-native-reanimated` as required dependencies, neither of which the source imports.
- **Doc claims code actively contradicts**: `sheet.mdx` states "The sheet automatically handles safe area insets" — `sheet.tsx` has no `react-native-safe-area-context` import at all and hardcodes offset values; `toast.mdx`'s "Custom Animations" section shows a legacy `Animated.spring(...)` example when the component is built entirely on Reanimated's `withSpring`; `accordion.mdx` documents web-only DOM `data-state`/`data-disabled` attributes that cannot exist in React Native.
- **Clean counter-examples worth preserving as the model to follow**: `avatar.ts`, `card.ts` (props only — false a11y claim separately), `combobox` (hand-written, accurate), `picker.ts`, `media-picker.ts` (the most self-aware file found — it correctly documents its own dead `placeholder` prop as unused), `alert-dialog.ts`, `popover.ts` (the most accurate file found — 7 sub-components, every prop matches exactly), `gallery.ts`, `table.ts`.

### 3.5 Accessibility gaps by control type (concrete, not generic)

- **Binary/selection controls** (`checkbox`, `switch`, `radio`, `toggle`): zero `accessibilityRole`/`accessibilityState` across all four. `checkbox` and `radio` additionally reuse `BORDER_RADIUS` (26px, a corner-rounding constant) as their touch-target size, landing under the 44×44 WCAG 2.5.5 / Apple HIG minimum with no `hitSlop` to compensate — `toggle`, which correctly uses the `HEIGHT` (48px) token, passes by coincidence. The three controls also use three different controlled-prop naming conventions (`checked`/`onCheckedChange`, `value`/`onValueChange`, `pressed`/`onPressedChange`) for functionally near-identical components.
- **Modal/overlay surfaces** (`bottom-sheet`, `sheet`, `action-sheet`, `alert-dialog`, `popover`): none set `accessibilityViewIsModal`, so Android TalkBack has no explicit signal to trap focus inside the overlay.
- **`input-otp.tsx`** hides its real, interactive `TextInput` off-screen (`left: -9999, opacity: 0`) and drives it via decoy `Pressable` "slot" elements with no `accessibilityLabel` per slot — a screen-reader focus ring has no perceivable target to land on, a materially worse gap than "just missing a role." It also lacks `textContentType="oneTimeCode"`/`autoComplete="one-time-code"`, forgoing native SMS-autofill entirely.
- **Charts**: see §3.2 — 0/18 have any accessibility props; native per-datapoint semantics aren't feasible for SVG rendering, so the realistic fix is a single synthesized summary label per chart, with `progress-ring-chart` as the one exception capable of full native `progressbar` semantics.

### 3.6 Styling and performance consistency

- ~1 in 4 files use `StyleSheet.create`; the remaining ~3 in 4 use inline `style={{}}` objects, which lose React Native's style-object caching/identity benefits. The split doesn't correlate cleanly with component complexity — some of the largest files (`date-picker`, `color-picker`) use inline styles throughout.
- Memoization is rare: `React.memo` in ~4% of files (`spinner`'s `AnimatedDot`/`AnimatedBar`, `gallery`'s `FullscreenImage`, `audio-waveform`'s `Bar` are the confirmed positive examples). The primitives most worth memoizing — `text`, `view`, `card` — given they're the most-instantiated leaf components in the library, are unmemoized.
- No `useMemo` found anywhere across all 18 charts — geometry, angle/arc math, and stacking calculations recompute from scratch on every render regardless of whether `data` changed. `treemap-chart`'s `squarify()` layout algorithm is the most expensive unmemoized computation found (effectively O(n²) per level, rerun on every unrelated parent re-render).
- **Unvirtualized lists**: `gallery.tsx`'s main thumbnail grid renders via `.map()` inside a plain `ScrollView` — while the same file's fullscreen viewer correctly uses `FlatList` with `getItemLayout`/`windowSize` tuning, proving the pattern is known but not applied consistently. `table.tsx` has the same issue when its `pagination` prop is set `false`, removing the only size guard on a generic data table — exactly the component most likely to be handed a large dataset. `carousel.tsx` has the same pattern with lower real-world risk given typically small, fixed children counts.
- `Dimensions.get('window')` is cached at module scope (rather than using `useWindowDimensions()`) in `bottom-sheet.tsx`, `sheet.tsx`, `tabs.tsx`, `carousel.tsx`, `gallery.tsx`, `onboarding.tsx`, and `color-picker`-adjacent code — stale after device rotation or on foldables.
- Hardcoded, device-agnostic safe-area offsets (instead of `useSafeAreaInsets()`, despite `react-native-safe-area-context ~5.7.0` being an available dependency) were found in `action-sheet.tsx`, `bottom-sheet.tsx`, and `sheet.tsx` — under Expo SDK 57's Android edge-to-edge default (and notch/Dynamic-Island iOS devices), these will misplace headers/content. `sheet.mdx` makes this worse by explicitly (and incorrectly) claiming safe areas are handled automatically.

### 3.7 Confirmed functional bugs (not accessibility or documentation gaps)

These are runtime-behavior bugs, independent of the doc-drift and accessibility findings above:

1. **`tabs.tsx`**: `allTabContents`, a mutable object holding tab content, is declared at **module scope** and mutated by every mounted `CarouselTabContent` instance. Since `enableSwipe` defaults to `true`, this path is live by default. Any two `Tabs` components rendered with overlapping `value` strings — two tab groups on one screen, or a previous screen's `Tabs` not yet unmounted in a navigator stack — silently overwrite each other's content, and entries are never cleared (a retained-reference leak for the app's lifetime).
2. **`video.tsx`**: `nativeControls` is destructured with a default but the underlying `VideoView` hard-codes `nativeControls={false}` regardless of what's passed — confirmed broken by the repo's own bundled `video-native-controls` demo, which sets `nativeControls={true}` expecting native chrome that will never appear. Separately, the exported `VideoRef` type documents imperative methods (`play`, `pause`, `seekTo`, etc.) that are never wired up via `useImperativeHandle` — `forwardRef` passes the ref straight through to the native view, so calling any documented method crashes at runtime.
3. **`share.tsx`**: `subject` is assigned onto the wrong argument of RN's `Share.share()` call (content instead of options), making it a silent no-op per RN's own source; `title` is gated to iOS-only when RN's source treats it as the Android-facing field — applied on the platform where it does least, dropped on the platform where it would work. `testID` and `fallbackMessage` are declared props that are never destructured or spread through, making them fully inert.
4. **`link.tsx`**: the internal-navigation render path recomputes `asChild` from `typeof children` rather than respecting the caller-supplied value — a prop that's silently discarded, not just undocumented.
5. **`treemap-chart.tsx`**: the documented, typed `children` field for hierarchical/nested data is declared but never read by the layout algorithm — nested data is silently dropped with no warning.
6. **`progress-ring-chart.tsx`**: the optional `label` is rendered as an `SvgText` sibling of `<Svg>` rather than a child of it — react-native-svg elements are only supported as `<Svg>` descendants, so this documented, first-class prop is likely broken as shipped.
7. **`date-picker.tsx`**: `error`/`errorStyle` are effectively non-functional — the error string is never rendered as visible text anywhere, and the only effect (a label-color tint) is nested inside a conditional that requires `label` to also be set, so `error` passed without `label` has zero visible effect.
8. **`image.tsx`**: internal `onLoadStart`/`onLoadEnd`/`onError` handlers (which drive the built-in loading spinner and error fallback) are wired before `{...props}` is spread, so a consumer using any of the three documented public callbacks of the same name silently overwrites the internal handler and permanently breaks the loading/error UI.
9. **`avatar.tsx`**: `AvatarFallback` never actually triggers automatically on image load failure — nothing connects `AvatarImage`'s error state to `Avatar`'s children selection, contradicting the component's own stated purpose ("a fallback for representing the user").
10. **`media-picker.tsx`**: uses the deprecated `ImagePicker.MediaTypeOptions` enum (confirmed via current Expo docs) instead of the current `mediaTypes` string-array API, and requests permissions eagerly on mount with no `Linking.openSettings()` escape hatch for permanently-denied permissions. The required `app.json` config-plugin entries are documented as automatic but are confirmed **absent** from the actual playground app, creating a real first-run iOS crash risk for anyone following the docs into a plain scaffold.
11. **`color-picker.tsx`**: every gesture-pan frame unconditionally calls `runOnJS(updateColor)`, forcing a full React re-render (including a `hexToRgb` regex that only accepts exactly 6 hex digits, silently resolving shorthand/alpha hex to black) on every touch-move, when Reanimated natively supports UI-thread color interpolation via `useAnimatedStyle`/`interpolateColor` for this exact use case.
12. **Chart NaN/divide-by-zero bugs**: `pie-chart`, `doughnut-chart`, `polar-area-chart`, `radial-bar-chart`, and `radar-chart` all compute a ratio against a `total`/`maxValue` derived from the dataset with no guard for an all-zero dataset, producing `NaN` geometry and silently broken (invisible) rendering. `pie-chart`/`doughnut-chart` additionally mishandle a single 100%-share segment — the arc's start and end points coincide, which SVG's arc command cannot draw, per the SVG spec.
13. **`radial-bar-chart.tsx`/`progress-ring-chart.tsx`**: SVG gradient `id`s are hardcoded literal strings with no per-instance namespacing — two same-config instances on one screen (explicitly cited as a primary "Dashboard Widgets" use case in `progress-ring-chart`'s own docs) will collide, a real risk on `react-native-web` where SVG `<defs>` become real, globally-unique-required DOM ids.
14. **`theme-provider.tsx`**: builds its theme object inline in the component body on every render with no `useMemo`, so every `useTheme()` consumer across the app re-renders on any `ThemeProvider` re-render, not just real color-scheme changes — confirmed against React's own documented context-memoization guidance, and consequential since this provider is mounted at the app root.

### 3.8 Theme system

`semanticColors` (`success`/`warning`/`info`/`error`, light+dark) is exported from `colors.ts` as a fully separate object from `Colors`, never merged in. `useColor`'s parameter type (`keyof typeof Colors.light & keyof typeof Colors.dark`) can therefore never resolve a `semanticColors` key — `useColor('success')` doesn't type-check today. A repo-wide grep confirms `semanticColors` has **zero consumers** anywhere in `packages/registry/src` — it is fully dead code. `colors.mdx`'s own "Semantic Usage" best-practice example papers over this by hardcoding `semanticColors.light.success` directly, which ignores the active theme and breaks dark mode for anyone who copies it verbatim — the exact failure mode the theme system exists to prevent. `badge.tsx`'s `success` variant is a concrete casualty: it's forced to reuse the iOS-accent `green` token instead of a purpose-built semantic token, because the real one is unreachable.

`globals.ts` exports exactly 4 scalar constants (`HEIGHT`, `FONT_SIZE`, `BORDER_RADIUS`, `CORNERS`) — no spacing scale, no typography scale. `globals.mdx` itself invents a `spacing: {xs,sm,md,lg,xl}` object and a typography block in its own usage examples, built from a file that exports none of those values — the documentation is effectively already asking for the expansion the source lacks.

### 3.9 Testing and process

Zero component-level tests exist anywhere in `packages/registry` (confirmed via filesystem search across all 79 items and their surrounding directories). The one existing test (`tests/registry.test.ts`) validates registry metadata (schema, dependency cycles, baseline snapshot), not component rendering or behavior. There is no changeset history for `@bna-ui/registry` component changes — only the CLI package (`bna-ui`) has an active `.changeset/` history — meaning the component library itself has never been formally versioned or had migrations tracked.

## 6. Prioritized Roadmap

Phased by dependency order and blast radius, not just raw priority — later phases assume earlier ones are done where that materially changes the work (e.g., writing accessibility tests is easier once accessibility props actually exist).

### Phase 0 — Stop the bleeding (do first; fixes real bugs, not polish)

- Fix the Rules-of-Hooks violation in all 15 affected chart components (§3.1) — mechanical, low-risk, no public API change. This is the only finding in the audit that represents an actual crash under ordinary usage.
- Fix `tabs.tsx`'s module-scope `allTabContents` bug (§3.7 #1) — real data corruption / memory leak, live by default.
- Fix `video.tsx`'s dead `nativeControls` prop and non-functional `VideoRef` (§3.7 #2).
- Fix `action-sheet.tsx`'s missing dependency declaration (§3.3) — currently ships a broken install on fresh projects.
- Fix `media-picker.tsx`'s deprecated API usage and missing `app.json` plugin documentation (§3.7 #10) — real first-run crash risk.
- Rewrite `camera-preview.mdx`'s fictional API reference and remove the `expo-av` install instruction.

### Phase 1 — Accessibility remediation, batched by category

Given the scale (78 of 79 items have zero real accessibility props), this is the largest phase by item count but individually cheap per component — most fixes are 1-3 lines of additive `accessibilityRole`/`accessibilityState`/`accessibilityLabel`. Suggested order: binary controls (checkbox/switch/radio/toggle — highest-traffic, most WCAG-explicit) → buttons/feedback → overlays/modals (`accessibilityViewIsModal`) → primitives → media/camera → charts (single-label baseline per §3.2) → scrolling/misc. Correct the false `meta.ts` accessibility claims (§3.2) in the same pass as each component, since verifying and fixing the doc is nearly free once the real props are added.

### Phase 2 — Documentation-drift remediation

Fix the confirmed prop-doc mismatches cataloged in §3.4 and per-row in §5 — fabricated props (`image.full`, `mode-toggle.style`, `accordion.disabled`), missing real props (`button.haptic`, `input.type/rows`, `tabs.enableSwipe/value/onValueChange`, `bottom-sheet.disablePanGesture`, `file-picker.variant`, `date-picker`'s range type), missing `meta.ts` `types` fields entirely (`carousel`, `onboarding`, `parallax-scrollview`, `view`, `bottom-sheet`, `toast`), and the standalone false/wrong-API doc claims (`useBottomTabOverflow`, `useColorScheme`, `useModeToggle`, `theme-provider`, `sheet`'s safe-area claim, `toast`'s animation-library example). This phase benefits from adding an automated drift check (see Phase 6) so it doesn't need repeating.

### Phase 3 — Functional bug fixes (the rest of §3.7)

`share.tsx`'s `subject`/`title` routing, `link.tsx`'s `asChild` override, `treemap-chart`'s ignored `children` field, `progress-ring-chart`'s broken `label` placement, `date-picker`'s non-functional `error` prop, `image.tsx`'s callback-override bug, `avatar.tsx`'s non-automatic fallback, `color-picker.tsx`'s re-render pattern, the chart NaN/divide-by-zero bugs, the SVG gradient-id collision risk, and `theme-provider.tsx`'s missing `useMemo`.

### Phase 4 — Testing foundation

Zero component tests exist today (§3.9). Stand up a component test harness (React Native Testing Library or equivalent) and prioritize tests for the highest-risk/most-complex components first: `date-picker` (1147 lines, discriminated union modes), `tabs` (after the Phase 0 module-scope fix, to lock in the correct behavior), `combobox`, `camera`/`camera-preview`/`video`, and at least one chart per geometry family (line, pie, treemap) to guard against Rules-of-Hooks regressions. Accessibility props added in Phase 1 give these tests something concrete to assert against.

### Phase 5 — Styling, performance & consistency

`StyleSheet.create` migration for the inline-style majority (optional — low urgency, mostly a consistency call rather than a correctness one); `React.memo` for the primitives (`text`, `view`, `card`) and other confirmed-safe candidates; `useCallback` for list-item handlers (`toggle`'s `ToggleGroup`); `useMemo` for all chart geometry calculations (§3.6) — pair this with the Phase 0 hook-extraction refactor since both touch the same render code; FlashList/FlatList adoption for `gallery.tsx`'s main grid and `table.tsx`'s rows (§3.6); `useWindowDimensions()` migration away from module-scope `Dimensions.get('window')` caching (found in 6+ components); `useSafeAreaInsets()` adoption in `action-sheet`, `bottom-sheet`, `sheet`, `gallery`.

### Phase 6 — Registry/dependency hygiene

Remove the ~14 unused `react-native-gesture-handler` declarations across charts and the handful of unused `registryDependencies` (`combobox`, `carousel`, `scroll-view`) (§3.3); add missing dependency declarations (`spinner`, `skeleton`); add `react-native-worklets` to every chart MDX's manual-install snippet; fix `tabs.ts`'s copy-pasted `view` description; fix `chart-container`'s unused `expo-image` dependency.

### Phase 7 — Theme system expansion

Merge `semanticColors` into `Colors` (or extend `useColor`'s type union) so success/warning/info/error tokens are actually reachable (§3.8) — this unblocks `badge`'s `success` variant and `toast`'s theme-awareness fixes from Phase 3/1. Add a `SPACING` scale (and consider a small font-size scale) to `globals.ts`, matching what its own docs already describe. Reconcile the three different controlled-prop naming conventions across `checkbox`/`switch`/`radio`/`toggle` (§3.5) — likely the single highest-effort, most consumer-visible change in this roadmap, since it touches public prop names; consider it a deliberate, version-flagged decision rather than a quiet fix.

**Resolution, decided during the Phase 0–8 fix pass (AUDIT_CHECKLIST.md):**
documented as intentional, not renamed. `checkbox`/`radio` use `checked`/
`onCheckedChange` (ARIA checkbox semantics), `radio`'s group selection and
`toggle`'s `ToggleGroup` use `value`/`onValueChange` (matching, correct
group-selection convention shared by both), and `toggle`'s standalone
`Toggle` uses `pressed`/`onPressedChange` (ARIA `aria-pressed` semantics).
Each name is independently well-motivated by the control it belongs to —
this isn't drift, it's three different ARIA vocabularies applied correctly
to three different interaction models. `packages/registry/package.json` is
`"version": "0.0.0"` and `"private": true` — never published or semver'd —
so there is no npm-level breaking-change concern, only source already
copied into consumer projects by `bna-ui add`, which defaults to skipping
files that already exist rather than overwriting them; a rename would
therefore only affect components a consumer hasn't installed yet, for a
purely cosmetic consistency win, while a permanent dual-prop deprecation
shim would have to live forever in copied-not-imported source with no
update channel to ever remove it. See `meta/checkbox.ts`, `meta/radio.ts`,
and `meta/toggle.ts` for cross-referencing notes on this decision.

### Phase 8 — Process

Start a changeset practice for `@bna-ui/registry` component changes (today only the CLI package has one) so future component changes are tracked and versioned. Consider a lightweight CI check that diffs each `meta/<name>.ts`'s documented props against the actual component's exported prop type, to prevent the Phase 2 drift from silently recurring — this is the single highest-leverage process fix available, since manual spot-checking is what allowed the drift in §3.4 to accumulate undetected across most of the library.

### A. Known limitations of this audit

- Static and documentation-based, not device/simulator-tested. Two specific claims should be verified on-device before being treated as certain: the exact Reanimated 4.5.0/worklets 0.10.0 compatibility pairing (conflicting secondary sources), and any behavior change resulting from Phase 0/3 fixes before shipping them.
- `WebFetch` access to `reactnative.dev` was unreliable in the research sandbox during several batches; those citations were corroborated via `WebSearch` snippets or a reader-proxy fetch of the same canonical URL instead of a direct fetch, and are marked as such in the relevant rows.
- Coverage is a single research pass per item, not an exhaustive one — some batches note their own single-spot-check caveats (e.g., "verified prop-doc match" reflects a line-by-line diff done once, not a standing guarantee).
- Impact/Priority ratings were normalized across the 11 independent research passes during aggregation, but remain a judgment call, not a formula — treat them as a starting point for triage discussion, not a final ranking.
